# How the prototype implements the blueprint

The blueprint describes a Next.js app, a worker and Postgres on a container host. This prototype has to live on GitHub Pages, which only serves static files, so the whole platform runs in the visitor's browser. Every rule in the blueprint is still enforced in code; what changed is where that code runs. This note records each substitution and every decision the blueprint left open.

## Where each part runs

| Blueprint | Prototype | Notes |
| --- | --- | --- |
| Next.js app with route handlers | A static single-page app (`index.html` + ES modules) | No build step. The route handlers' work lives in `src/services`, called directly by the UI. |
| Postgres through Prisma | `src/db`: an in-memory store with synchronous transactions and rollback, saved to IndexedDB | Tables match the blueprint's twelve, plus `StatusChange` (who changed what), `Brief` and `Dispute`. `LedgerEntry`, `ReputationEvent` and `StatusChange` refuse updates and deletes. |
| Worker polling a jobs table | `src/jobs/worker.js` polls the `Job` table inside the page every 300 ms | Same retry-then-fail behaviour. Failed jobs show in Admin → Jobs with a Retry button. |
| GitHub sign-in (Auth.js) | Demo personas | OAuth needs a server-side secret. The blueprint's M6 demo mode already calls for personas, so they are the only sign-in. |
| Platform LLM on a server key | Mock by default; Claude or an OpenAI-compatible endpoint with a key saved in the browser; optionally free providers (Gemini, Groq, OpenRouter free tiers, or Ollama) tried before Claude | The official Anthropic SDK is vendored (`vendor/anthropic-sdk.js`) and called with `dangerouslyAllowBrowser`, which sends the direct-browser-access header. Free providers are called over their OpenAI-compatible APIs with keys saved the same way. |
| File storage (disk or S3) | IndexedDB blobs | Same limits on size and type as the demo mode in M6. |
| zod | `src/lib/schema.js`, a small zod-style validator | Keeps the site free of runtime CDN dependencies, and emits the JSON Schema used for Claude's structured output. |
| React Flow graph editor | `src/app/views/graph.js`: a layered SVG layout plus a form-based tile editor | Nodes are keyboard-focusable, and there's a table view of the same graph. |
| Render or Fly.io | GitHub Pages | Each visitor gets a private copy of the world. Export and import it from Settings. |
| Playwright against the deployed stack | Playwright against the static site served by `scripts/serve.js` | The same tests run in CI. |

Because each browser is its own platform instance, "other people" are simulated. The **crowd** (`src/services/crowd.js`) lets every seeded contributor you aren't playing accept offers, submit sample work that meets the tile's automatic checks, review each other and vote on panels, after short human-like delays. It goes through the same API a person uses, so it can't bypass a rule. Personas you have played are never simulated.

## The disaggregation engine

The blueprint makes decomposition the Decomposer's job and leaves its method to the prompt. The prototype adds a rule-based engine, `src/decompose`, for three reasons: the mock must split *any* job well without a model, a model does better when it starts from a careful reading and a reference split, and a plan from any source needs an objective check of how separable it is.

- **Reading** (`analyze.js`). Sentences and bullet lists become components; each gets a kind of work (24 archetypes, from collect and clean to translate, design, software, media and finance), a count and whether it repeats per asset. Requirements are listed one per line with ids so coverage can be checked tile by tile.
  Long sentences are read the way a person would: a "with" list that ends in "for each" is a detail of the thing before it (a codebook "with a definition and an example quote for each"), a data file named with its columns ("a coded_all.csv with response_id, branch and theme(s)") sets the columns the batches and the merge use, "…, each with a rough cost" stays with the part it describes, "no more than 3 recommendations" is a part capped at three, and connectives ("Then", "Finally,") are dropped. The parts listed for a short document (three pages or 1,500 words or less) are what its writer covers, except work that stands on its own (costs, charts, tables of counts), which becomes a tile the document waits for. A piece that names its language ("a one-page Spanish summary") is written in that language instead of translated, and a summary of the report waits for the report.
- **Planning** (`pieces.js`). A conventions piece comes first whenever two or more people work in parallel. Named pieces follow; then the pieces a product takes for granted (a data pull and cleaning step behind charts, geocoding behind a map, a build step for a page, back end and screens built apart against an API contract); then layers (de-identification, per-language translation, one-voice editing, phone and accessibility testing, spot and agreement checks); then one assembly tile.
- **Sizing** (`rates.js`, `builder.js`). Throughput rates by kind of work and unit ("clean 120 listings an hour") turn counts into minutes; batches aim for 75 minutes (105 for translation, where context matters) and never exceed 120. Past 60 batches in one piece or 120 tiles in one plan, later ranges are left for a second phase with the same tiles.
- **Wiring**. Each tile lists `inputs` and `outputs` by file name; dependencies come from which tile makes each file a tile reads, choosing the closest producer. Batches of the same count align by range, so per-asset pipelines don't wait on other assets.
- **Budget**. Priority 3 then 2 tiles are cut first, then batch groups are trimmed from the end so every operation on the same rows stops at the same row, then whole pieces. What was left out is listed as phase two.
- **Grading** (`quality.js`). Parallel speedup of the core work, share of tiles in the 30–90 minute sweet spot, inputs that come from tiles the reader waits for, hidden dependencies, duplicate outputs, mixed-skill tiles, uncovered requirements, missing assembly and the share of automatic criteria give a score and grade. Each problem carries a fix (`ops.js`) the requester can apply in one click, on the breakdown page or a planned commission.

The new tile fields (`inputs`, `outputs`, `stream`, `phase`, `partOf`, `part`, `covers`, `priority`) are optional in the `TileDraft` schema, so older plans and model plans still parse; `repairGraph` infers missing inputs and outputs from the spec and deliverable text. The Claude Decomposer uses prompt `decomposer.v2` (v1 is kept), with the engine's compact analysis and reference plan in its input; `decomposer-refine.v1` runs once when a model plan grades below C and is kept only if it scores higher.

## The agent swarm

The blueprint's contributors are people. The swarm (`src/services/swarm.js`) adds jobs whose every step after submission is done by AI agents, without a second code path: agents are contributor accounts marked `isAgent`, and they act only through the services a person uses (`respondToOffer`, `claimFromBoard`, `submitWork`, `submitPeerReview`), so every rule, check, payout and reputation event applies to them.

- **Stopped jobs.** A job still marked running when the worker starts (the page closed or reloaded mid-job) is set back to pending. Resuming a swarm job whose planning stopped queues planning again, and the Swarm tab offers Plan again (`retryPlanning`).
- **Workforce.** A commission's `workforce` is `people` (the default) or `agents`. The Matcher ranks agents only for swarm jobs and people only for the rest; eligibility refuses the other side as a backstop. The crowd simulation never plays agents and never acts on swarm jobs; dispute panels are people only.
- **The autopilot.** On a swarm job the requester's steps are automatic: the `autopilot.v1` agent answers scoping questions (assumptions are marked "Assumption:"), the plan is adapted for agents and funded (over budget is accepted: the budget is a people-equivalent figure), a peer review no agent can take is settled with the Reviewer as the requester, and the delivery is signed off. The requester can pause and resume the swarm on the job; it pauses itself at the spend cap, after three failures of one task, or on an error it can't fix.
- **Adapting the plan** (`src/decompose/agents.js`). Agents have no body, and web access only through the research step below. Tiles whose step needs a person (interviews, recording, editing audio or video, transcription, outreach, physical work) become the kit that person needs, with Markdown and heading checks and an LLM check that a person could act on it alone; repeated batches of such steps become one kit. Live-data collection becomes one collection script on a labeled SAMPLE; fact-finding (venues, quotes, competitors, funders) must mark unchecked facts "(verify)"; publishing and device testing hand off to a person. When the requester attached no file, parallel batches over their material collapse to one sample run, and row-count checks downstream of any sample are dropped. Every such tile records `agentMode` and a `handoff`, and the deliverable lists them under "What a person still needs to do".
- **Doing a tile.** The worker agent receives the job, the tile, the accepted files its inputs name (from any earlier layer, not only direct parents), the attachments (only its rows for a batch tile), and on a revision the failed criteria with reasons and its previous files. Its validator runs the tile's AUTO rules on its files, so it fixes them before hand-in; after the retries the last parseable answer is handed in with its known problems (`runAgent`'s `bestEffort`) and review decides. Inputs are capped (60,000 characters in all, 16,000 per file).
- **Agent time and splitting** (`src/decompose/agent-time.js`, `src/agents/split.js`). An agent's time is mostly the tokens it writes, so each tile's expected time is estimated from its outputs (rows × tokens per row, with rewriting work such as translation priced by the attached table's row length; words for documents; fixed amounts for charts, JSON and scripts) plus thinking, at the model's writing speed: a rough default per model in `prices.js` until the swarm has timed three or more of the model's worker runs in this browser. Adapting a plan with `timing` folds prose batches with the same inputs into chunks up to the target time (all of a short draft into one tile, renamed without its batch suffix), marks longer row or section work with a `splitHint`, records `agentEstimate` on each tile, and gives the job an expected time along its longest chain. At run time a first attempt whose estimate passes the target gets `delegation` in its input only when `splitOffer` finds a split that saves 15 seconds or more and adds no more than the allowance (the lead's plan at the cache-write price, each part's reread of the shared context at the cache-read price, each part's own notes), within the spend cap. The worker prompt (`worker.v3`) renders the shared context as one block marked for the prompt cache and the per-call part (offer, part, revision) after it, so the parts, which start after the lead's call returns, read the cache; a mock provider counts cache writes and reads the same way. Each part is a logged worker call with `part: "i/n"`. Parts are validated (only their files; no nested splits), joined by code (tables stacked with repeated ids dropped, documents in order, JSON lists concatenated), and checked with the tile's AUTO rules; failures go to the lead as a revision-shaped fix call. Any failed part or invalid plan falls back to one whole call. Revisions, conventions, independent checks, kits and final assembly never split. Parts run on top of the agents-at-once limit and count against the swarm's rate-limit pool and spend cap.
- **Competition and supervision** (`src/services/competition.js`, `src/domain/supervision.js`; the swarm blueprint of 28 September 2026). With competition on (the default), `work()` hands each non-review tile to `compete()` instead of one worker call. The blueprint's five tables are nine here: `TaskSpec` (the spec: hard checks, weighted rubric, threshold, the competitors picked and why, the result), `Attempt` (one row per worker per round, with its stored files, tokens in, cached and written, and cost in millionths of a dollar), `Score` (check results, the supervisor's 0–4 marks per rubric item, rubric score, final score), `SupervisorAction` (every action with its reason, feedback and new child tasks, including your settlements), `WorkerStats`, `WorkerConfig` (strategy hint, parent, generation, status), `Lesson`, `LessonTrial` and `SupervisorAudit`. A tenth, `AgentMessage`, is the wire (below). Attempts, scores, actions, lesson trials and wire notes are append-only. With `finalists` set (Economy uses 2), only the best attempts go on to later rounds; the rest are recorded as losses. A revision may hand back `edits` (find a passage in its own prior draft, replace it) instead of whole files; `src/agents/edits.js` applies them (a passage must occur exactly once), and the worker's validator and the swarm see the finished files. The flow per task: blind round (competitors grouped by model, since caches are per model; in each group the first starts alone and the rest are released when its response starts streaming; the Anthropic provider streams any call with `onStart` and fires it on the first event) → hard checks → supervisor scores every attempt that handed in files → `decide()` → a second round when the blind round was flagged or failed (`reveal: auto`): by default a **notes round** (`exchange: notes`), where the finalists read one shared block with the supervisor's score and summary of every draft, the notes the competitors posted each other and each one's approach, plus (uncached) their own full draft and weakest items, and revise; or, with `exchange: drafts`, the older reveal round with every blind draft → re-score → accept, accept with a flag, send back (each finalist gets the supervisor's feedback, its own failed checks and weakest items, its own full draft, and the scores and notes of the last round), re-split (the `resplit.v1` agent splits by rows or sections under the same validator as a speed split; children compete in parallel with `part` inputs, are joined by code, and the parent's supervisor scores the join), or escalate. A competed submission carries `supervised` (winner, score, flag, per-criterion marks); verification records those marks as the LLM review (2 of 4 or better passes a criterion) instead of calling the Reviewer, and agent peer review is skipped unless the tile is high stakes. An escalated tile stays claimed with `supervision.state: "escalated"`, is skipped by the swarm and by claim expiry, and waits on the Supervision page. Learning, routing, evolution and audits follow the blueprint; the numbers are in `config.swarm` and `evolveConfigs`.
- **Where this departs from the swarm blueprint, and why.**
  - *The supervisor doesn't share the workers' cache.* The blueprint puts the task layer in one cache shared by the workers and the supervisor, but a cache entry belongs to one model and one system prompt, and the supervisor runs on a different model on purpose. The supervisor keeps its own layers (the job for an hour, the task and rubric for five minutes, shared by its blind, reveal and later rounds). Worker layers (`worker.v5`) are the system prompt (1 h, shared by every job), the job with the requester's whole files (1 h, byte-for-byte the same for every tile of the job), the task with its inputs and a snapshot of the wire (5 min), the round's notes or drafts (5 min), then the uncached suffix: playbook, config, strategy hint, personal lessons, own draft, feedback. The playbook moved out of the prefix so the control worker (who goes without it) shares the task layer with the others.
  - *The supervisor scores failed attempts too, blind to the checks.* The blueprint says rubric judgment applies to "what's left" after the checks. Here it scores every attempt without seeing the check results (a failed attempt still scores zero), because that is what makes "agrees with the hard checks" measurable for the supervisor's audit. When every attempt fails a check, no supervisor call is made.
  - *Hard checks are what a browser can run:* the tile's AUTO rules, every owed file present, no SAMPLE data when real data is in the inputs, and every cited URL present in the research or inputs. Code isn't executed and tests aren't run.
  - *The reveal round is conditional* (the blueprint's open question): by default it runs only when the blind round wasn't a clean accept, never when the supervisor can't judge the task or finds it too big; a sharp blind disagreement is flagged even if the reveal settles it. Settings can make it always or never.
  - *Competition on every task, or only where it pays* (the other open question): "on" competes everywhere with routing to two once a config wins ≥ 70% of six or more tasks of a type; "auto" also lets a config that wins ≥ 80% of ten or more work alone, still scored and sent back.
  - *Re-split notes feed the re-split agent, not the Decomposer.* Earlier re-split reasons for the same task type on other jobs go into `resplit.v1`'s input as `pastResplits`; the Decomposer's prompt is unchanged.
  - *Escalation goes to you, not to a parent task supervisor.* A child task that escalates makes its parent escalate with the reason; a top-level task comes to the Supervision page. Upstream flags reach later supervisors through `task.upstream`, and every flag reaches the root supervisor and the deliverable.
  - *Configs evolve on their overall record*, not per task type: a config under 15% wins over twelve or more tasks is retired (three stay active), one over 50% over six or more is cloned: first onto the next cheaper Claude model with its own strategy (`cheaperClones`, on by default; Fable → Opus → Sonnet → Haiku), then, once that has been tried, with a new strategy hint from a fixed bank. A config has its own `model` (none means the worker model from Settings). Routing ranks configs whose scores are within 0.03 cheapest first (by average cost per attempt), and adds a bonus of up to 0.05 for assists. A **challenger** config (`challenger: free | haiku | sonnet`) is always included in every competition in place of the lowest-ranked pick, stays out of evolution, and stops competing when Settings switch it off.
  - *Personal lessons have no control group*, since only one config reads them; their "without" side is that config's record on the task type before the lesson (at most ten tasks).
  - *A long tile's split for speed happens before the competition*: when a split is offered, the lead makes a short split-or-not call (`delegation.decideOnly`) that also warms the cache, and the parts compete; otherwise the whole tile competes.
- **Merges by code.** When a tile's CSV output is the stack of numbered batch files (`coded_01.csv`… → `coded_all.csv`), or a final assembly joins batch files of different kinds on a shared id column, the swarm computes the file itself and the agent writes only the rest. Merged files travel as a non-enumerable `precomputedFiles` property, so they never enter a prompt or an AgentRun log.
- **Review.** With competition off, agent work gets the automatic checks and the Reviewer like anyone's (with competition on, see above). Peer review goes to another agent for PEER criteria and high-stakes tiles; the first-five and 20% sampling rules exist to build trust in new people and are skipped for agents.
- **Limits and money.** Swarm jobs use their own rate-limit pool (300 calls per 10 minutes) for every agent, including the Reviewer and Assembler on those jobs. Tile pay still moves through escrow to the agent accounts, so the ledger rules hold and the Swarm tab can show what the same tiles would pay people next to the model spend. Agents are exempt from the per-contributor submission limit, and their minutes are left out of estimate calibration.
- **Pacing.** With the mock, each agent task waits about a second in the browser so the run is watchable; with a real model the calls set the pace.
- **Web research.** Tiles marked `webResearch` by the adapter (outside facts: prices, venues, funders, public data, rules, research; never work on the job's own data) get one research call before the work, on the worker model, with Anthropic's server tools: `web_search_20260318` and `web_fetch_20260318` (dynamic filtering, `response_inclusion: "excluded"`) on models that take them, the basic `web_search_20250305` / `web_fetch_20250910` otherwise, capped per tile in Settings. It's a separate call because web search always returns citations, which can't be combined with a JSON output format; the research call returns cited Markdown, and the worker's structured call gets the notes and sources. The provider resumes `pause_turn` up to five times, sums searches and page reads into the AgentRun, and returns the cited, fetched and searched URLs. The research is stored on the tile and reused on revisions. A 400 saying web search isn't enabled (an organization setting in the Claude Console) turns research off for the session with one note on the job.
- **Prompt caching and cost.** AgentRuns record `tokensCacheWrite` (and `tokensCacheWrite1h`, the hour-long part) and `tokensCacheRead` beside uncached `tokensIn`; costs price five-minute writes at 1.25× input, hour-long writes at 2×, and reads at each model's cache-read price. Calls that share a prefix with calls after them (every worker call, supervisors across rounds, a split's lead, its parts, and the fix pass) mark cache breakpoints, and such a call also marks its system prompt for an hour (`cacheSystem`; free, since a write bills each token once); a request marks at most four, hour-long ones first. The requester's whole files are clipped the same way for every tile (first, up to 60% of the input budget) and ride in the job layer, so a job with a long manuscript writes it to the cache once and every tile rereads it at the cache price. Admin → Cost per commission shows what the cache, batches and free models saved (`savingsUsd`).
- **Half-price batches** (`createBatcher` in `src/llm/anthropic.js`). With `batch` on, the swarm's worker, supervisor and reflection calls (never ones with server tools) are collected for two seconds and sent as one Message Batch; the provider polls it (15 s, backing off to 60 s) and hands each caller its message or error. Runs record `batch: true` and cost half. Batches are asynchronous (minutes, up to 24 hours), so jobs take longer; a batch in flight when the tab closes is lost and its calls are sent again.
- **The wire** (`AgentMessage`, `wireFor`, `taskNotes`, `assistsFrom`). A worker may post up to three notes (to `team`: the agents on the job's other tiles; to `rivals`: the competitors on its task, read next round) and lists the note ids it relied on (`usedMessages`, kept only for notes it was shown). Each tile's input carries a snapshot of the job's team notes from other tiles (newest 15, 4,000 characters), taken once so every competitor reads the same cached block. When an attempt is accepted, each note it relied on from another config earns that config an assist on the note's task type (`WorkerStats.assists`); the leaderboard shows notes and assists, and assists raise a config's rank a little. One-agent tiles post notes too (without a config, so they earn no assists). The Supervision page lists the wire with how many attempts, and accepted ones, used each note.
- **Free models first** (`src/llm/free-chain.js`, `router.freeFirst`). Settings can switch on Gemini's, Groq's and OpenRouter's free tiers and Ollama, each with a model and a key saved in the browser. A free-first route tries them in order through `createFreeChain`; a provider that answers 429 rests (an hour for a daily quota, else as long as it asks, at least a minute). The route carries the paid route as `fallback`, and runAgent switches to it, from a fresh start, after any failed free attempt (no answer, or an answer that fails its schema or validator), with one extra attempt for it. Free routes serve light work (Reviewer first pass, matcher notes, autopilot answers, reflections) when `free.light` is on, the `free` challenger config, and one-agent tiles when `freeSolo` is on; planning, supervision, assembly, research and heavy reviews never use them. Cloud free tiers only ever see jobs marked Public; Ollama (local) may take any job. Free runs are logged with provider `free:<id>`, cost $0, and a shadow model for what Claude would have cost. **Free models only** (platform provider `free`, `router.freeOnly`) routes every tier, every swarm agent and every challenger to the free chain with no fallback; the chain waits (patience three minutes) for a provider resting after a per-minute limit and fails with `free_quota` (not retried) when all are out of daily quota. Private jobs use only local providers unless `free.privateToo`. Web research is off. Each provider's reply ceiling (`maxOutput`) caps `max_tokens`.
- **Models.** Heavy (Scoping, Decomposer, Assembler, Reviewer escalation) defaults to Claude Opus 5.5, light (first-pass Reviewer, offer notes) to Claude Haiku 4.5, swarm workers and research to Claude Sonnet 5.5, and checks of other tiles' work to Opus 5.5. Each agent sets `output_config.effort` on models that take it (the swarm's workers and supervisor take theirs from Settings, `workerEffort` and `checkEffort`: medium by default, low in the Economy preset); requests to Opus 5.5, Sonnet 5.5, Fable 5.1 and Opus 5 go to the beta endpoint with `fallbacks: "default"`, and the provider drops the fallback, then the JSON format, if the API rejects them.
- **Guards from the first real run.** A tile whose inputs include tabular data made upstream isn't live-data collection. Merge tiles (by kind, title or output name) receive every batch file upstream of them, grouped by the plan's `partOf` and ordered by part, and say in their notes what was merged or why nothing was. A worker's output labeled SAMPLE or placeholder while its inputs hold real tables is refused and retried. Recommendation, cost and budget tiles carry a criterion that every number names its source and every cost shows its arithmetic; the Reviewer on swarm jobs sees the tile's inputs and research sources. The deliverable leads with the final tile's main document.

- **Planning a big job** (`src/services/commissions.js`). The Decomposer runs at high effort with a 64,000-token reply limit; the Anthropic provider streams any request allowed more than 16,000 tokens and waits for the final message, so long replies aren't cut by HTTP timeouts. A reply cut off at max_tokens carries its usage on the error (so the run is logged and priced), and runAgent retries it at the next lower effort. Model plans are parsed with a looser tile schema than people's edits (`PlanTile`: any title up to 300 characters, any key, skill tag, estimate and tier), and the Decomposer's validator rejects only a plan with no work tiles; long titles are clipped to 80 characters and everything else is fixed by `repairGraph`, because a rejected plan is minutes of work lost and a rewrite takes as long. Long calls (more than 16,000 output tokens) stream with a 30-minute limit and no SDK retries; runAgent retries, waiting out rate limits and overload as the API's retry-after asks (at least 5 s, doubling), and a timed-out or cut-off reply retries at lower effort. The one-shot plan is not retried: when it fails, or from the start when the engine's reference plan has more than 12 tiles or the attachments hold more than 20,000 characters of text, planning is staged: `decomposer-outline.v1` returns the skeleton (workstreams; each tile's key, title, outputs, dependencies and requirements), validated for unique keys, known dependencies, no loops and one maker per file; then `decomposer-stream.v1` writes each workstream's tiles in full, exactly the skeleton's keys, four streams at a time. The stream calls share the job and the skeleton as one cached block (the first starts alone, the rest once it streams), and the skeleton's dependencies and outputs override the details so the streams fit. Both prompts are the Decomposer's rules (`decomposer.v2`) plus a stage-specific ending. **Departure from the working rule "retry twice, then fail the job for a human":** if staged planning also fails, the engine's own plan is used and the plan's notes say so, because on a swarm job nobody is waiting to unstick a failed planning job; a requester can re-plan.
- **Reading attachments** (`src/lib/extract.js`, `src/services/files.js`). Word (.docx) and Excel (.xlsx) files are zip archives of XML: the zip is read with the browser's `DecompressionStream('deflate-raw')`, Word paragraphs become lines (headings as `#`, list items as `-`, table rows as `|` cells), tracked insertions and deletions (and moves) are kept as `{+…+}` and `[-…-]`, comment anchors as `[comment n]` with the comments and footnotes listed at the end; each Excel sheet becomes CSV under a `## Sheet:` heading, with shared and inline strings and booleans. PDF text is read from the page content streams (`DecompressionStream('deflate')`, object streams included), in page-tree order, through each font's ToUnicode character map, and with word gaps judged from the fonts' glyph widths (so kerning doesn't split words and PDFs without space characters still get spaces); encrypted PDFs and pages without text (scans) give none, and the file's summary says so. The text is stored beside the upload (`textKey`), read wherever a file's text is (`readFileText`), summarized as a "document" (words, headings, sheets, pages, tracked changes, comments, the opening 1,200 characters), redacted on restricted jobs, and passed to the Scoping agent (4,000 characters a file) and the Decomposer (8,000 a file, 40,000 in all) as `documents`, marked as data. Agents doing tiles read up to 60,000 characters a file and 150,000 in all.
- **Revise-and-respond jobs** (`src/decompose/revision.js`). A job to revise a document (manuscript, paper, chapter, proposal, report…) in answer to reviewers', referees' or editors' comments gets its own plan instead of the sentence-by-sentence reading: triage every comment into `comment_matrix.csv` (comment, decision, section, plan) and a style sheet (conventions phase), revise up to five sections at the same time (the attached manuscript's own headings in groups, or the usual sections of a paper), write the point-by-point response letter, check the revision against every comment, and assemble the clean manuscript and the final letter. "Keep the numbers" and "in my voice" become criteria on every section; a request for tracked changes becomes a handoff to make them with Word's Compare.
- **Word copies** (`src/lib/docx.js`). The deliverable download carries a .docx of the deliverable report and of each Markdown document the final assembly made, written with no library (headings, paragraphs, lists, quotes, tables, bold, italic, code, links); `{+inserted+}` and `[-deleted-]` marks become real tracked changes.

## Decisions the blueprint left open

**Ledger sign convention.** `amountCents` is the entry's effect on the commission's escrow: funding is positive; payouts, fees and refunds are negative. A contributor's earnings are the negated sum of their payout entries. A closed commission's entries sum to exactly zero, and no prefix may go below zero; `postLedger` rolls back any transaction that would overdraw.

**Paying for peer review.** Funding a plan escrows tile pay, the 10% fee, and a *peer-review reserve*: one 15-minute review at each work tile's tier, plus its fee. Reviews are paid from the reserve. If revisions need more reviews than the reserve holds, the requester's escrow is topped up automatically and the receipt says why. Unused reserve is refunded at sign-off.

**When the fee is charged.** On each payout (tile, review or partial pay), in the same transaction.

**Who can review.** The rule is someone with earned reputation in one of the tile's skills (at least one accepted tile in it) who never worked on the commission. A fresh platform has almost no earned reputation, so until someone has it, a self-rated level of 3 or more in the skill qualifies (`config.reviewerBootstrapLevel`). If nobody independent of the commission is eligible, matching relaxes to "anyone who didn't work on *this* tile", and the tile records that it did. The requester can always settle a pending review themselves.

**Who the first-five rule counts.** A contributor's accepted work and integration tiles. Reviews don't count toward it.

**Planned REVIEW tiles vs. sampled peer reviews.** REVIEW tiles in the Decomposer's graph are QA passes: ordinary paid tiles whose deliverable is a review report. Sampled peer reviews are separate dynamic tiles, created when a submission passes its automatic and LLM checks. They check the submission's PEER criteria, or all of its criteria when sampled.

**Revision rounds.** A failed round goes to REVISION. The third failure (after two revisions) reopens the tile to others. The failing contributor is excluded from that tile, and the requester can grant partial pay (funded by a small top-up) for usable work.

**Disputes.** Accepted tiles stay accepted, and their pay is never clawed back. If two of three panelists vote to reopen, the platform creates *rework* tiles funded by a platform quality guarantee (an `ESCROW_FUND` entry from the platform account). The original contributor gets a `DISPUTE_REOPENED` reputation event. At sign-off, leftover escrow is refunded to the most recent funder first, so an unused guarantee returns to the platform. Panelists are the three contributors with the most accepted work in the disputed skills who never worked on the commission. The basic panel is unpaid.

**Estimate calibration.** The blueprint feeds the median actual-to-estimate ratio back to the Decomposer. Here, after parsing, the ratio is also applied deterministically to each tile (rounded to 5 minutes, clamped to 15–120). Pay then rises reliably, whether or not a given model follows the hint. The tile shows its original and calibrated estimates.

**Reputation event weights.** `ACCEPTED` and `REVIEW_COMPLETED` count as accepted and as an attempt. `REVIEW_FAILED` and a second or later `CLAIM_EXPIRED` count as attempts. A first expired claim counts for nothing, and `DISPUTE_REOPENED` removes one accepted credit. The `delta` column stores display points; R is always recomputed from the reasons.

**Tile languages.** Tiles carry an optional `languages` list (the Decomposer schema gained this field). Eligibility requires sharing one of them, or the commission's language when the list is empty.

**Offer windows and the board.** People who let an offer lapse or declined it aren't re-offered that tile, but they can still claim it from the open board. Releasing a claim is free and excludes you from that tile.

**Signing key.** Each instance generates its own Ed25519 key in WebCrypto, with a non-extractable private key kept in IndexedDB. The public key is published at Admin → Signing key. Exported records name their issuer key; the Verify page checks a record against this instance's key, the key named in the record, or any pasted key. In a server deployment there would be one platform key; here there is one per browser, which the page says plainly.

**The guided demo.** While the guide is running, the crowd leaves the visitor's commission alone until the visitor has claimed one of its tiles as a contributor, so there's still work left to try.

**Rate and file limits.** 40 non-mock LLM calls per 10 minutes (300 more for the agent swarm), 6 commissions an hour per requester, 20 submissions an hour per contributor, 5 MB per file, 10 files and 20 MB per submission, and an allow-list of file types. All of these live in `src/domain/config.js`.

## What isn't real

The money, the people other than you, and (by default) the model. The mock agents are deterministic: the Decomposer is the rule-based disaggregation engine in `src/decompose` (see below), the Reviewer uses transparent heuristics (and flags text addressed to it), and the Translator fills its brief from the tile spec. Connect Claude in Settings to see the real agents on the same pipeline; every call is logged with its prompt version, tokens and cost.
